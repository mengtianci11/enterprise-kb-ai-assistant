# 设计文档：语义缓存（v3.3，P1-⑤ 的可验证子集）

> 原计划 P1-⑤「多模型路由 + 本地推理 + 语义缓存 + 离线模式」需要一个 GPU 才能验证本地推理；
> 其中**语义缓存**不依赖 GPU、收益可测量，因此单独落地（其余部分维持"规划"状态）。

---

## 1. 为什么做

生产环境里员工反复问同类问题（年假、报销、差旅标准……）。不缓存时每次问答都要走：

```
问题 → 查询改写(LLM) → 向量检索(embedding) + BM25 → RRF → Cross-Encoder 重排 → 生成
```

其中改写与重排都是**外部模型调用**，延迟与成本都高。语义缓存把「相同/近似问题」的结果直接复用：

- 延迟：秒级 → 百毫秒级（实测 **16.2 倍**加速）；
- 成本：跳过改写与重排的 API 调用（一次命中省 2-4 次外部调用）；
- 副作用可控：只缓存**检索结果**，不缓存答案。

---

## 2. 设计：缓存键必须包含权限与版本

```
cache key = 语义相似度匹配（问题向量） + 权限范围指纹 + 索引版本
```

| 组成部分 | 作用 | 不带的后果 |
| --- | --- | --- |
| 问题向量（cosine ≥ 0.97） | 语义命中（近似问法也能复用） | 只能精确匹配，命中率低 |
| **权限范围指纹**（可见文档集合哈希；管理员为 `all`） | 防止越权命中 | A 用户的机密结果被 B 用户拿到（**严重安全事故**） |
| **索引版本**（文档增删时 +1） | 文档变更后整体失效 | 删了文档还能搜到（数据不一致） |

### 2.1 为什么不做「答案级缓存」

答案受多轮上下文影响，且一旦命中会**绕过权限过滤与检索**，风险大于收益。
因此缓存放在**检索层**：命中的是"某问题的 Top-5 资料"，答案仍由模型基于资料生成（保留引用与权限语义）。

### 2.2 生命周期

| 事件 | 行为 |
| --- | --- |
| 命中 | 返回结果快照（深拷贝，避免调用方修改污染缓存） |
| TTL 到期（默认 600s） | 读取时惰性清理 |
| 文档增删（`rebuild_after_change`） | `bump_version()` → 版本号+1 且清空全部条目 |
| 容量超限（默认 512） | 淘汰最旧（LRU 近似） |
| 近似重复写入 | 同 scope 下相似度 ≥ 阈值则替换，避免堆积 |

## 3. 实测效果（真实 API，本机）

同一问题「公司年假是怎么规定的？工作满几年会增加？」连续检索两次：

| 轮次 | 耗时 | 说明 |
| --- | ---: | --- |
| 首次（完整管线） | **2345 ms** | 改写 + 向量 + BM25 + RRF + 重排 |
| 缓存命中 | **144 ms** | 仅计算问题向量（embedding 一次） |
| 加速比 | **16.2×** | 结果完全一致（内容逐条比对通过） |

缓存统计：`{"entries": 1, "hits": 1, "misses": 1, "hit_rate": 50.0, "version": 0}`

> 生产环境命中率取决于问题重复度；制度类知识库通常 20%–40%。

## 4. 安全验证

| 测试 | 结果 |
| --- | --- |
| 不同权限范围不互相命中 | ✅（scope 指纹不同 → miss；管理员 `all` ≠ 普通用户集合） |
| 文档变更后缓存失效 | ✅（`bump_version` 后旧 scope 也命中不了） |
| 相同问题第二次命中且不再调用改写 | ✅（测试中计数 `query_rewrite` 调用次数） |
| 相似问法命中（0.95 阈值） | ✅ |
| TTL 过期 | ✅（模拟时间流逝） |
| 容量上限淘汰 | ✅ |

## 5. 接入方式

```python
# AppState 中注入
self.cache = SemanticCache(
    max_entries=settings.CACHE_MAX_ENTRIES,
    ttl_seconds=settings.CACHE_TTL_SECONDS,
    min_similarity=settings.CACHE_MIN_SIMILARITY,
    enabled=settings.CACHE_ENABLED,
)
self.rag.cache = self.cache
```

配置项（`.env`）：

```dotenv
CACHE_ENABLED=true
CACHE_MAX_ENTRIES=512
CACHE_TTL_SECONDS=600
CACHE_MIN_SIMILARITY=0.97
```

观测：`GET /admin/config` 返回 `cache` 字段（entries / hits / misses / hit_rate / version）。

## 6. 取舍与边界

| 决策 | 收益 | 代价 |
| --- | --- | --- |
| 进程内缓存（LRU+TTL） | 零依赖、实现简单 | 多副本各自缓存，命中率下降；可换 Redis 共享 |
| 只缓存检索结果 | 安全（不绕过权限） | 生成仍要调 LLM，端到端节省有限 |
| 阈值 0.97 | 精度优先，避免"近义但不同"误命中 | 命中率略低 |
| 指纹用可见文档集合哈希 | 精确防越权 | 权限频繁变化时命中率下降（可接受） |

---

## 7. 后续

1. Redis 共享缓存（多副本共用，key 同上，value 序列化）；
2. 按热度做 LRU/TTL 分级（高频问题长 TTL）；
3. 与质量门禁联动：缓存命中率纳入监控，异常下降告警；
4. 答案级缓存（需把会话上下文与权限纳入键）——仍在评估，暂不实施。
