# 评测集扩容：24 → 115 题（v3）

> 目的：让"失败分类学"有足够样本，让引用/冲突等后续能力有可度量的评测基础。
> 原有 24 题保留为 v2（CI 基线口径不变），新增题集独立为 `eval/dataset_v3.json`。

## 1. 为什么要扩

C 阶段的真实结论：

- 24 题 × 5 策略 = 120 个评测点，只产出 **6 个**非满分点 → 失败样本不足，分类统计不可信；
- LLM-as-Judge 的 24 题全部 5.0 分（天花板效应）→ 无法从质量维度发现失败；
- 结论：**样本量是当前评测体系最大的短板**。

## 2. 设计

### 2.1 五类题目

| 类型 | 数量 | 考察点 | 示例 |
|---|---:|---|---|
| `single_hop` | 74 | 单条事实精确检索 | "密码多久必须更换一次？" |
| `procedure` | 12 | 流程/步骤类 | "网口不通应该按什么顺序排查？" |
| `paraphrase` | 10 | 口语化改写（词面不匹配） | "在家办公怎么连公司内网？" |
| `multi_section` | 9 | 跨段落/多条件组合 | "备份文件和日志分别保留多久？" |
| `unanswerable` | 10 | 知识库未收录 → 必须拒答 | "公司的 CEO 叫什么名字？" |
| **合计** | **115** | | |

### 2.2 文档分布

| 文档 | 题数 | 文档 | 题数 |
|---|---:|---|---:|
| 员工手册.md | 16 | 网络架构与运维.md | 11 |
| 招聘管理制度.md | 14 | 项目管理系统说明.md | 11 |
| 技术运维手册.md | 13 | BI报表中心说明.md | 10 |
| 信息安全管理办法.md | 11 | 产品使用指南.md | 8 |
| 云ERP常见问题.md | 11 | （不可答） | 10 |

### 2.3 数据结构

在原字段（`question` / `doc` / `evidence`）基础上新增 `type` 与 `note`：

```json
{
  "id": 31,
  "question": "密码多久必须更换一次？",
  "doc": "信息安全管理办法.md",
  "evidence": ["密码每90天须更换一次"],
  "type": "single_hop",
  "note": ""
}
```

`evidence` 必须是**语料原文的精确子串**——这样才能稳定定位"标准答案分块"，避免人工标注漂移。

## 3. 三道质量校验（`scripts/validate_dataset.py`）

1. **文档存在**：`doc` 必须能在 `eval/corpus` 找到；
2. **evidence 为原文子串**：防止手滑改写导致金标定位失败；
3. **分块后可检索**：按生产分块配置重建 chunk，确认 evidence 至少出现在一个 chunk 中——避免"跨块证据"造成必错题。

> 第 3 道校验立了大功：直接发现了一个**真实分块 bug**（见 `eval/incidents.json` 的 `INC-09`）——
> `技术运维手册` 的"## 部署流程"下，有序列表首项 `1. 上传发布包至 /opt/app/release 目录；` 整块丢失，
> 且列表项被误当章节标题（`[技术运维手册.md > 2. 执行 ./deploy.sh …]`）。

## 4. 如何运行

```bash
# 1) 合并并校验（生成 eval/dataset_v3.json）
python scripts/expand_dataset.py

# 2) 单独校验
python scripts/validate_dataset.py eval/dataset_v3.json

# 3) 跑 v3 评测（真实 API，115 题 × 5 策略，约 15 分钟）
python scripts/eval_rag.py \
  --dataset eval/dataset_v3.json \
  --report docs/eval_report_v3.md \
  --last-run eval/last_run_v3.json \
  --details eval/last_run_details_v3.json

# 4) 导出 v3 失败样本
python scripts/export_failures.py \
  --details eval/last_run_details_v3.json \
  --dataset eval/dataset_v3.json \
  --out eval/failures_v3.json
```

> v2（24 题）仍是 CI 门禁口径，`scripts/eval_rag.py` 无参数时行为不变。

## 5. 结果

v3 运行完成（2026-10-25，真实 API）：

| 指标 | v2（24 题） | v3（115 题，计分 105） |
|---|---:|---:|
| full Hit@3 | 100.0% | 100.0% |
| full Hit@5 | 100.0% | 100.0% |
| full MRR@5 | 97.9% | **99.5%** |
| full Top-1 | 95.8% | **99.0%** |
| 失败问题 / 评测点 | 6 / 120 | 13 / 525 |
| 失败档案总数 | 13 | **22** |

**修复后（同义词扩展 + INC-09 分块修复）**：v3 的 BM25 Hit@3 从 98.1% → **100%**、Hybrid 从 98.1% → **100%**；召回类失败清零，剩余失败全部是 Top-1 排序噪声（见 `docs/failure_taxonomy.md` §9）。

**一个反直觉但重要的发现**：v3 的指标**比 v2 更高**（MRR 97.9 → 99.5）。
原因不是系统变强了，而是新题以**单跳事实题**为主（74/105），难度低于 v2 中"多跳 + 口语化 + 跨段"的混合题。
结论：**题量增加 ≠ 难度增加**；下一步应补多跳、冲突、长文档题，而不是继续堆单跳题。

（完整报告：`docs/eval_report_v3.md`；失败档案：`eval/failures_v3.json`）

## 6. 已知局限（诚实声明）

1. **语料小、题密度高**：9 篇小文档平均 12.8 题/篇，存在同义重复与"背答案"风险；题目质量依赖作者，未做多人标注一致性检验；
2. **无真实冲突用例**：语料内没有互相矛盾的事实，冲突类题目留到 B 阶段（扩语料后补）；
3. **不可答仅测倾向**：10 道不可答题验证拒答倾向，不替代权限边界测试；
4. **`type` 分布不均**：single_hop 占 64%，多跳类仅 9 题，后续需补跨文档多跳。

## 7. 扩容带来的直接收益

- 失败样本从 6 条提升到可支撑分类统计的量级（目标 ≥30 条）；
- 可按 `type` 做分组指标（例如"口语化题 vs 单跳题"的召回差异）；
- 为 A（引用校验）、B（冲突归因）提供可对比的评测底座。
