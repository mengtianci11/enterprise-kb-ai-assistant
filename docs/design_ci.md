# 设计文档：质量门禁（P0-④）

> 对应《企业级升级方案 v3.0》P0-④：让「不回归」成为可自动执行的事，而不是靠人记得跑评测。
> 本文档说明三道门的设计、基线与阈值机制、验证证据与取舍。

---

## 1. 为什么需要（问题本质）

RAG 系统的典型风险不是「功能报错」，而是**效果静默劣化**：

| 改动 | 单测能否发现 | 效果是否变化 |
| --- | --- | --- |
| 改分块大小/策略 | ❌ 不报错 | ⚠️ 召回可能变差 |
| 换 embedding / 重排模型 | ❌ 不报错 | ⚠️ 指标波动 |
| 调整 RRF 参数、Top-k | ❌ 不报错 | ⚠️ Top-1 下降 |
| 权限过滤改动 | ✅ 部分可测 | ⚠️ 可能误伤有权文档 |

单测只能证明「逻辑对」，证明不了「效果没退化」。企业级做法是把**离线评测做成 CI 硬门禁**：
指标相对基线下降超过容忍度 → 阻断合并，必须显式说明或更新基线。

## 2. 三道门

```
┌─────────────┐   ┌───────────────┐   ┌──────────────────────┐
│ 1. 单元测试  │ → │ 2. 密钥扫描    │ → │ 3. 指标门禁（可选）    │
│ 147 项离线   │   │ 无 sk- 明文    │   │ 对比基线，回归即失败   │
└─────────────┘   └───────────────┘   └──────────────────────┘
```

### 2.1 单元测试（离线、必跑）
`pytest -q`：147 项，不依赖网络与密钥，任何 PR 都会执行。

### 2.2 密钥扫描（必跑）
`python scripts/scan_secrets.py`

- 优先扫描 **git 跟踪的文件**（CI 中即真正要发布的内容）；无 git 时扫描「上传白名单」；
- 规则：`sk-[A-Za-z0-9_-]{20,}`（OpenAI 兼容 Key 形态）；
- 背景：本项目历史遗留文件（原版备份、早期练习脚本）中曾硬编码过真实 Key，
  这条门禁把这些文件挡在仓库之外；
- 命中即失败，输出 `文件:行号 -> sk-abc***`（打码，避免二次泄露）。

### 2.3 指标门禁（可选，需 Secret）
`python scripts/check_metrics.py`

- **基线**：`eval/baseline.json`，由 `--update-baseline` 生成（含指标、评测集 md5、分块配置、阈值）；
- **当前结果**：`eval/last_run.json`，评测脚本每次运行自动写出（机器可读）；
- **对比**：逐策略 × 逐指标比较，`delta < -阈值` 判失败；
- **默认容忍度（百分点）**：

| 指标 | 阈值 | 理由 |
| --- | ---: | --- |
| Hit@3 | 2.0 | 核心召回指标，敏感 |
| Hit@5 | 2.0 | 兜底召回，敏感 |
| MRR@5 | 3.0 | LLM 改写有随机性（temperature=0.3），给 3pp 波动空间 |
| Top-1 | 5.0 | 受重排波动影响较大 |
| 文档命中@5 | 2.0 | 文档级召回 |

- **评测集变更检测**：`dataset_md5` 不一致时默认失败（防止改题库粉饰指标），
  可用 `--allow-dataset-change` 显式放行。
- **无密钥仓库/fork**：脚本检测不到 Key 时输出 `[SKIP]` 并以 0 退出，保证公开仓库可跑。

## 3. CI 流程（.github/workflows/ci.yml）

| Job | 触发 | 说明 |
| --- | --- | --- |
| `test` | push / PR | `pip install -r requirements-dev.txt` + `pytest -q` |
| `secret-scan` | push / PR | `python scripts/scan_secrets.py` |
| `eval-gate` | push / PR（needs: test） | 有 `SILICONFLOW_API_KEY` 则跑评测门禁，否则跳过；上传评测报告 artifact |

> 说明：`eval-gate` 依赖真实模型 API，放在独立 job 并做「有密钥才跑」的降级，
> 避免 fork 或未配置密钥的仓库无法通过 CI——这是公开项目常见的折中。

---

## 4. 本地使用

```bash
# 日常提交前
pytest -q
python scripts/scan_secrets.py

# 建立了基线之后
python scripts/check_metrics.py --from-last-run     # 快速对比（不调用 API）
python scripts/check_metrics.py                    # 重新评测再对比（真实 API，约 3 分钟）
python scripts/check_metrics.py --update-baseline  # 确认效果提升后更新基线
```

## 6. 取舍与边界

| 决策 | 收益 | 代价 |
| --- | --- | --- |
| 评测放 CI 而非每次提交本地跑 | 强制、可追溯 | 真实 API 成本（约 3 分钟 / 次，几十次调用） |
| 无密钥自动跳过 | 公开仓库/PR 可用 | 无密钥时质量门禁不生效 |
| 容忍度按指标分别设置 | 尊重 LLM 随机性 | 阈值需随评测集变化调整（md5 校验兜底） |
| 基线只存汇总指标 | 简单可读 | 无法定位到"哪道题退化"（后续可存 per-question 明细） |

## 7. 后续（P1/P2）

1. 把门禁扩展到**分块 A/B 指标**（`eval_chunking.py` 纳入同一基线体系）；
2. 增加 **LLM-as-Judge** 端到端质量分（答案正确率/忠实度），当前只评检索；
3. 每次发布自动生成「指标趋势图」（Grafana / GitHub Pages 看板）；
4. 按题目维度存明细，门禁失败时直接给出「哪几道题变差了」。
