# 方案设计：WikiFusion —— 私域文档 + Wikipedia/Wikidata 的双源证据融合问答

> 状态：**提案（Draft v0.1）**，未实现，未提交代码。
> 目标读者：作者本人 + 面试官。
> 一句话：把「企业私域 RAG」和「公共 Wiki/Wikidata」做成**双源证据融合 + 可验证引用**的问答系统，用评测证明「什么时候该信谁」。

---

## 1. 项目定位

### 1.1 要解决的问题

单一知识源都有硬伤：

- **纯私域 RAG**：覆盖面窄，用户问「劳动法规定年假多少天」「GDPR 是什么」时答不了；
- **纯 Wiki/Web RAG**：回答不了企业内部的「我们公司年假怎么请」「销售提成怎么算」，且引用粒度粗、容易过时。

企业真实场景里，用户的问题往往**横跨两者**：例如「按劳动法和公司制度，我今年能休几天年假？」——需要同时检索法规（公共）和公司制度（私域），并在冲突时说明依据。

### 1.2 目标（可量化）

| 目标 | 指标 | 验收线 |
|---|---|---|
| 双源问题答得对 | 自建双源评测集 EM / 人工正确率 | ≥ 80% |
| 引用可验证 | Citation Precision / Recall | ≥ 0.85 / ≥ 0.80 |
| 冲突能识别 | 冲突用例正确归因率 | ≥ 90% |
| 不该答的不答 | 不可答问题拒答率 | ≥ 95% |
| 延迟可接受 | P95 端到端 | ≤ 8s（CPU） |

### 1.3 明确不做（控制范围）

- ❌ 不下载全量中文维基 dump（用子集 + 在线 API 兜底）
- ❌ 不做 GPU 训练 / 微调（复用 bge-m3 + LLM API）
- ❌ 不做多租户/权限体系（沿用现有项目的能力即可，本项目聚焦证据融合）
- ❌ 不追求「完美融合」——只追求**可解释、可评测**的融合

## 2. 背景：Wiki 的缺点与已有解法

| Wiki 的缺点 | 具体表现 | 对应技术 |
|---|---|---|
| 长文 + 段落碎 | 一个条目几十段，答案散落多处 | 分段检索 + rerank + 邻段扩展 |
| 多跳 | 「A 的导师的母校」要跨 2–3 个条目 | 迭代检索（IRCoT / self-ask）/ Agent 多步 |
| 实体歧义 | 「苹果」是水果还是公司 | 实体链接到 Wikidata QID |
| 关系型问题 | 「谁是谁的导师」文本里不一定直说 | Wikidata 三元组 / KG 检索 |
| 全局性问题 | 「这批文档主要在讲什么」 | GraphRAG 社区摘要 / 层次聚类 |
| 过时与冲突 | 条目更新滞后、不同来源矛盾 | 修订时间 + 来源可信度 + 冲突检测 |
| 引用粗 | 只说「来自维基百科」 | 段级/句级引用 + 引用校验 |
| 不覆盖私域 | 企业内部制度查不到 | 双源融合（本方案） |

相关方向（供答辩引用）：

- GraphRAG：图 + 社区摘要回答全局问题 —— <https://ar5iv.labs.arxiv.org/html/2404.16130>
- HippoRAG：知识图谱上的 Personalized PageRank 做多跳检索 —— <https://dl.acm.org/doi/abs/10.5555/3737916.3739818>
- WikiRAG：Wikidata 知识图谱 + 社区更新 + RAG —— <https://www.semanticscholar.org/paper/WikiRAG%3A-Revisiting-Wikidata-KGC-Datasets-with-and-Diffallah/2b5a1d86100af509426d58bae3a90a128aa7f252>
- ES-RAG：事件-实体子图引导检索 —— <https://dl.acm.org/doi/10.1007/978-981-92-3432-5_27>
- E²GraphRAG / MeshRAG：层次化摘要索引 —— <https://www4.comp.polyu.edu.hk/~xiaohuang/docs/2026ACL_MeshRAG.pdf>
- 多跳 RAG 评测（HotpotQA / 2Wiki）—— <https://aclanthology.org/2025.emnlp-main.1151.pdf>
- 带引用的生成（CoT + citation）—— <https://ojs.aaai.org/index.php/AAAI/article/download/29794/31374>

**本项目的差异点**：不新造检索算法，而是把「双源 + 事实 + 引用校验 + 冲突处理」四件事做成可量化、可复现的工程闭环。

## 3. 总体架构

```
                         ┌─────────────────────────────┐
用户问题 ──► 查询理解 ──► │ 实体链接（Wikidata QID）      │
                         │ 意图/来源路由（私域/Wiki/双源）│
                         └──────────────┬──────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
  私域检索（复用）                Wiki 检索                       Wikidata 事实
  BM25 + FAISS + RRF            段落 hybrid 检索                  实体三元组 / infobox
  + bge-reranker                链接图 1-hop 扩展                 （按需 API / 本地子集）
        │                               │                               │
        └───────────────┬───────────────┴───────────────┬───────────────┘
                        ▼                               ▼
                证据统一（EvidenceUnit）          冲突检测（NLI / LLM 判定）
                来源 / 时间 / 可信度 / 文本        私域 vs Wiki 不一致时标注
                        │
                        ▼
                融合排序（来源先验 + 时效 + 一致性）
                        │
                        ▼
            生成（带 [E1][E2] 引用）──► 引用校验 ──► 不通过则删句/重写/拒答
                        │
                        ▼
                    答案 + 证据列表 + 冲突说明
```

### 3.1 证据单元（统一抽象）

```python
EvidenceUnit = {
    "id": "E1",
    "source": "private" | "wiki_para" | "wikidata_fact",
    "text": "...",                 # 事实类为 "Q42 出生地 → 伦敦"
    "meta": {
        "doc_id" / "page_id": ...,
        "rev_id" / "updated_at": ...,   # 时效依据
        "title": ..., "section": ..., "url": ...,
        "score": 0.0,                    # 检索分
        "authority": 0.0,                # 来源先验（私域制度 > Wiki）
    },
}
```

统一抽象的好处：排序、冲突检测、引用校验都只面对一种结构。

### 3.2 路由（关键设计）

| 路由结果 | 触发条件 | 行为 |
|---|---|---|
| `private` | 问题含企业专有名词 / 出现在私域文档 | 只检索私域 |
| `wiki` | 通用知识、实体定义 | 只检索 Wiki |
| `both` | 检测到「公司 + 法规」「我们 + 标准」等组合 | 双源并行 |
| `none` | 检索分低于阈值 | 明确拒答 |

路由实现：轻量规则（关键词/实体类型）+ LLM 分类兜底；**规则优先**，因为可解释、可测试。

### 3.3 冲突处理（本项目的"记忆点"）

当私域与 Wiki 对同一事实给出不同值时：

1. **不静默覆盖**：两个值都保留，标注来源与时间；
2. 按策略排序：企业制度类问题 → 私域优先；通用法规 → Wiki 优先；
3. 输出形如：
   > 公司制度规定年假 5 天（来源：员工手册 v3，2026-03）；国家法定为 5 天（来源：Wikipedia，2026-01）。两者一致。

冲突检测：对语义相同的证据对做 NLI/LLM 判定（矛盾/蕴含/无关），只对高相似度对做，控制成本。

### 3.4 引用校验

生成后逐句检查：

1. 抽取句子中的 `[E#]`；
2. 计算句子与证据的蕴含/支持度（embedding 相似度 + LLM 判定）；
3. 不支持的句子：删除 / 要求重写 / 整题降级为"无法确认"；
4. 输出指标：Citation Precision（引用的证据里有多少真支持）、Citation Recall（支持的证据有多少被引用）。

## 6. 评测方案（差异化核心）

### 6.1 数据集

1. **HotpotQA / 2Wiki 子集**：多跳能力，标准 EM/F1；
2. **自建双源集（100 题）**，四类：
   - 私域-only（20）：只有公司文档能答；
   - Wiki-only（20）：通用知识；
   - 双源一致（20）：两边都有且一致；
   - **双源冲突（20）**：两边不一致，考察归因；
   - 不可答（20）：两边都没有，考察拒答。

### 6.2 指标

| 指标 | 定义 |
|---|---|
| EM / F1 | 标准答案匹配（HotpotQA 口径） |
| Support Recall@k | 金标证据是否被召回 |
| Citation Precision / Recall | 句级引用是否被证据支持 |
| Refusal Accuracy | 不可答问题正确拒答 |
| Conflict Attribution | 冲突用例是否正确说明"以谁为准 + 为什么" |
| P95 Latency / Cost | 端到端延迟与每题 token 成本 |

### 6.3 消融（必须有）

| 配置 | 目的 |
|---|---|
| BM25 only | 基线 |
| dense only | 基线 |
| hybrid（现网） | 现有能力 |
| + 链接图扩展 | 图结构收益 |
| + Wikidata 事实 | 结构化收益 |
| + 冲突检测 | 归因收益 |
| + 引用校验 | 可信度收益 |

### 6.4 门禁

沿用现有 CI 思路：评测结果写 `eval/last_run_wiki.json`，基线回归超阈值即失败；引用精确率单独设门禁。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 数据下载慢/大 | 阻塞 | 用 HotpotQA 自带段落；zhwiki 只取子集 |
| Wikidata API 限流 | 不稳定 | 本地缓存 + 降级到 infobox |
| 引用校验成本高 | 延迟/费用 | 只校验含事实的句子；批量调用 |
| 中英文评测混杂 | 结论不清晰 | 英文用 HotpotQA/2Wiki，中文只做演示 |
| 范围膨胀 | 做不完 | 严格按 1.3「不做」清单 |
| 与现有项目重复 | 简历上像同一项目 | 明确差异：双源/引用/冲突，非检索算法 |

## 10. 面试预答

1. **为什么不直接用 Wiki 的 API 就行？** —— API 只给文本，缺消歧、事实校验、冲突处理；本项目证明"怎么用"而不是"能用"。
2. **为什么不用 GraphRAG 全家桶？** —— 全局摘要成本高；先用轻量链接图 + 三元组验证收益，再决定是否上社区摘要。
3. **冲突时听谁的？** —— 按问题类型定策略，且必须**显式告知用户**，而不是静默选一个。
4. **引用怎么保证不瞎编？** —— 生成后逐句校验支持度，不支持就删/重写/拒答，并量化 Citation P/R。
5. **数据量够吗？** —— 评测用公开多跳集，演示用 zhwiki 子集；规模不是重点，闭环和指标才是。
