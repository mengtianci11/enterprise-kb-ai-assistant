# 设计文档：会话持久化与三层记忆（P0-②）

> 对应《企业级升级方案 v3.0》问题 4：对话记忆在内存里（重启后多轮上下文就丢，虽然文档不丢）。
> 本文档说明**为什么不用 LangGraph 自带的 checkpointer 做会话历史**、三层记忆如何实现、验证证据与取舍。

---

## 1. 目标

| 目标 | 验收方式 |
| --- | --- |
| 重启后多轮上下文不丢 | 重启服务后同会话追问"我刚才问了什么"，能准确复述 |
| 长会话 token 可控 | 上下文 = 固定轮数窗口 + 摘要，不随会话长度线性增长 |
| 会话可管理 | 列表 / 详情 / 重命名 / 删除 / 按用户隔离 / TTL 清理 |
| 不破坏现有能力 | 88 项既有测试全部保持通过（升级后 107 项全绿） |

---

## 2. 为什么不用 MemorySaver / SqliteSaver

LangGraph 的 checkpointer 保存的是「整条线程状态」，有两个不符合本项目需求的地方：

1. **无法按 token 预算裁剪**：`create_agent` 每次调用都会把线程内全部历史交给模型，长会话成本线性上升；
   LangGraph 的裁剪需要自定义 middleware，复杂度高且与 Agent 内部状态强耦合。
2. **数据不可直接运营**：会话/消息需要用于列表、统计、审计与后续的用户画像，藏在 checkpoint blob 里不便于查询。

**决策**：会话历史由业务层（SQLite 表）管理，每次请求**显式构造上下文**：`摘要 + 最近 K 轮 + 本次提问`，
Agent 以「无状态 + 显式上下文」方式调用。代价是失去工具调用中间状态的跨轮保留（知识库问答场景不需要），
换来**可控的 token 成本**与**可查询的会话数据**。

> 可选能力保留：`build_agent(..., checkpointer=...)` 仍支持注入 SqliteSaver，需要原生线程记忆时可直接启用。

## 3. 三层记忆

```
┌──────────────────────────────────────────────────────────┐
│ 第 3 层：长期记忆（跨会话）                                 │
│   conversations.summary —— 滚动摘要，随会话累积            │
├──────────────────────────────────────────────────────────┤
│ 第 2 层：摘要记忆（本会话的旧消息）                         │
│   超出阈值的历史消息 → LLM 压缩为 ≤800 字要点               │
├──────────────────────────────────────────────────────────┤
│ 第 1 层：工作记忆（最近 K 轮原文）                          │
│   list_messages(limit=2K) 直接进入上下文                   │
└──────────────────────────────────────────────────────────┘
```

### 3.1 工作记忆
- 每轮请求携带最近 `CONTEXT_WINDOW_TURNS` 轮（默认 6 轮 = 12 条消息）；
- 上下文 token 与轮数呈**常量关系**，与会话总长无关——这是 token 成本可控的根源。

### 3.2 摘要记忆（滚动摘要）
触发条件：消息总数 ≥ `SUMMARY_TRIGGER_MESSAGES`（默认 12）。

```python
pending = messages(id > summarized_upto)        # 尚未摘要的消息
to_summarize = pending[:-SUMMARY_KEEP_RECENT]   # 保留最近 6 条不摘要
summary = llm(旧摘要 + to_summarize)            # 增量合并压缩，≤800 字
update_summary(conv_id, summary, to_summarize[-1].id)   # 游标前移，避免重复摘要
```

关键设计：
- **`summarized_upto` 游标**：记录已摘要到的消息 id，增量摘要、天然幂等；
- **保留最近 KEEP_RECENT 条**：避免把「刚说过的话」也压缩掉，保证工作记忆的语义连续；
- **后台线程执行**：摘要需要一次 LLM 调用（约 2-5 秒），放在响应之后异步跑，不增加问答延迟；
- **失败不影响主流程**：LLM 不可用只写 warning，会话照常可继续。

### 3.3 会话管理
`conversations` / `messages` 表，按 `(user_id, client_key)` 唯一。前端生成 `client_key`（随机串），
后端据此取/建会话——用户隔离由 `user_id` 保证，跨用户访问返回 404（不泄露存在性）。

- 列表：`GET /conversations`（按更新时间倒序）
- 详情：`GET /conversations/{id}`（仅本人）
- 重命名：`PATCH /conversations/{id}`
- 删除：`DELETE /conversations/{id}`
- TTL：启动时清理超过 `CONVERSATION_TTL_DAYS`（默认 180 天）的会话
- 标题：首问前 40 字自动生成

## 5. 取舍与边界

| 决策 | 收益 | 代价 |
| --- | --- | --- |
| 业务层管理上下文而非 checkpointer | token 可控、数据可运营、实现简单 | 工具调用中间状态不跨轮保留 |
| 摘要用 LLM 压缩 | 语义保留好 | 每次触发一次 LLM 调用（后台异步，不阻塞） |
| 最近 K 轮原文 + 摘要 | 准确性与成本的平衡 | 极长会话中早期细节只能靠摘要（有损） |
| 用户隔离严格（仅本人可见） | 隐私安全 | 暂无"分享会话"能力（P2 再加分享链接） |
| TTL 180 天 | 控制库体积 | 过期会话不可恢复（归档策略待补） |

## 6. 后续（P1/P2）

1. **长期记忆（用户级）**：把高价值摘要沉淀为 `user_memory` 向量库，跨会话召回偏好与历史结论；
2. **语义摘要检索**：不只用"最近 K 轮"，而是按当前问题检索相关历史片段（类似 Mem0）；
3. **会话分享**：生成带权限校验的分享链接；
4. **流式摘要**：把摘要做成流式，降低感知延迟；
5. **多端同步**：会话列表与消息增量拉取（WebSocket）。
